# Local two-tier topology in kind (#10)

Design §1.1: apps → **otel-agent** (DaemonSet, one per node) → **otel-gateway**
(Deployment, 2–4 replicas) → ClickHouse. Run everything from WSL2 (Ubuntu) in the repo root,
with Docker Desktop running.

```bash
make kind-up        # cluster `traceblame` (1 control plane + 2 workers), namespaces, Secrets
make kind-deploy    # images, ClickHouse (Altinity operator + CHI), NATS, Postgres, migrations, agent, gateway, trace-assembler
make bench-scaling  # span loss / split traces while the gateway scales 2 -> 4 -> 2; assembler lag
PROFILE=low STAMPS=1 RUN_NAME=low make bench-scaling  # per-stage lag at 2 x 10 traces/s, no scaling (#57)
make kind-clickhouse-persistence  # ClickHouse keeps its data across a CHI pod deletion (#58)
make kind-down      # deletes the cluster and ALL its data, ClickHouse included
```

## Layout

| Path | What |
|---|---|
| `kind-config.yaml` | Cluster shape. The API server port is fixed at 16443, because Docker Desktop on WSL2 refuses some random host ports. |
| `collector/agent.yaml` | The agent: OTLP with `basicauth` (one htpasswd user per tenant), `memory_limiter`, normalizer (`tenant_source: auth`, content stage), loadbalancing exporter (`routing_key: traceID`, k8s resolver, mTLS), and a file-backed queue (512 MiB, bytes sizer). |
| `collector/gateway.yaml` | The gateway: OTLP with mTLS (agents' CA only), `memory_limiter`, a second normalizer pass (keeps the agent's tenant), `tail_sampling`, and the stock ClickHouse exporter into `otel_traces_ingest` (ADR-0004). |
| `collector/gateway-bench.yaml` | Bench-only overlay: stamps `traceblame.bench.gateway` with the pod name, so the report can tell which gateway stored a span. |
| `collector/agent-bench-stamps.yaml`, `collector/gateway-bench-stamps.yaml` | Bench-only overlays (#57, `STAMPS=1`): `transform` processors stamp each span with the wall clock (`traceblame.bench.t_*_ns`) at the agent's first processor, the gateway's first processor, after `tail_sampling` and before the ClickHouse exporter, for the per-stage lag in `evals/reports/pipeline-lag-stages-*.md`. They ship in the ConfigMaps; only the bench adds them to the args, and restores the plain args on exit. `tests/scripts/test_bench_overlays.py` keeps the stamps and `transform` out of every other config. |
| `collector/eval-tenants.env` | `TRACEBLAME_EVAL_TENANTS`, the tenants whose eval and fault-injection markers are kept (#36). One ConfigMap, `eval-tenants`, feeds the agent and the gateway, so both normalizer passes use the same list. Empty by default. |
| `collector/latency-thresholds.env` | `tail_sampling` latency thresholds per service (generated by `loadgen thresholds`; source and date are in the file). |
| `manifests/` | Namespaces, the CHI, the agent DaemonSet with its EndpointSlice-only Role, the gateway Deployment with its Services and NetworkPolicy, NATS JetStream (`40-nats.yaml`), Postgres (`50-postgres.yaml`) and the trace-assembler (`60-assembler.yaml`). These are checked by kubeconform in pre-commit. |

## Decisions

- **Tenant (ADR-0005).** The agent overrides `aegis.tenant.id` with the authenticated
  htpasswd user. The gateway accepts only agents, by mTLS client certificate plus a
  NetworkPolicy, and keeps that value.
- **Eval and fault-injection traces (#36, ADR-0005).** The gateway keeps every trace that
  carries `aegis.eval.run.id` or `aegis.fault.injection.id`. Both normalizer passes keep a
  marker only for tenants in `eval_tenants`, and drop and count the rest in
  `traceblame_normalizer_eval_marker_rejected_total`. kind allowlists only `tenant-eval`,
  the tenant of eval runs (`make fixtures-agentic-rag`, #12; `make fixtures-runbook-agent`, #13); `tenant-a` and `tenant-b` may not
  mark traces. To change the list, edit `collector/eval-tenants.env` and run
  `make kind-deploy`, which restarts the agents and the gateways together. The shims and
  `faults/` set the markers (#12, #13, #14).
- **ClickHouse data (#58).** The CHI's data directory (`/var/lib/clickhouse`) is a PVC on the
  `standard` StorageClass (`rancher.io/local-path`, 20 Gi requested, not enforced). The
  operator keeps the PVC (`reclaimPolicy: Retain`) when it recreates the StatefulSet or when the
  CHI is deleted. local-path stores it under the node's `/var/local-path-provisioner`, on the
  Docker volume kind gives each node's `/var`. So the data survives a deleted pod and a restart of
  the node containers (Docker Desktop, Windows update, `wsl --shutdown`).
  - **`make kind-down` deletes the data.** `kind delete cluster` removes the node containers
    together with their `/var` volumes.
  - To start ClickHouse empty without kind-down, delete the CHI and its PVC
    (`kubectl -n observability delete chi traceblame && kubectl -n observability delete pvc -l clickhouse.altinity.com/chi=traceblame`),
    then run `make kind-deploy`.
  - **Switching an existing cluster.** On a cluster created before #58, the first
    `make kind-deploy` makes the operator recreate the StatefulSet with the claim. ClickHouse
    then starts empty on the new volume, and the migrations in the same run recreate the schema.
  - `make kind-clickhouse-persistence` checks the mount and the PVC. It writes a marker into a
    scratch database (`persistence_check`, never the migrated schema), deletes the CHI pod,
    waits for Ready and checks the marker.
  - The node-restart check is manual:
    1. `make kind-clickhouse-persistence MODE=write` prints a token.
    2. Restart Docker Desktop and wait for `kubectl --context kind-traceblame get nodes` to be
       Ready.
    3. Run `make kind-clickhouse-persistence MODE=verify TOKEN=<token>`.
- **No NATS from the collector.** `natsexporter` v0.164.1 cannot publish to JetStream. The
  gateway exports to ClickHouse only; the trace-assembler (#35, ADR-0003) polls
  `trace_arrivals` by arrival time instead. NATS (`observability`) carries only what our own
  services publish with publish-ack: `trace.completed`.
- **Trace-assembler (#35).** Two replicas in `traceblame` share the partitions by leases in
  Postgres (`assembler_partitions`); the watermark advance is fenced by the lease epoch. Its
  thresholds are the ConfigMap `assembler-config` (grace, poll interval, window, lease TTL,
  duplicate window, partition count). NATS and Postgres are single-server and ephemeral here (Postgres on an `emptyDir`: it survives a
  node restart, not a deleted pod).
  The migrations of both databases run in `make kind-deploy`. The assembler uses the
  gateway's ClickHouse user, a demo shortcut. Alerts: `deploy/alerts/` (not deployed: this
  cluster has no Prometheus outside the runbook sandbox).
- **memory_limiter.** The cluster configs use `limit_percentage`, which works with the
  container memory limits. Local smoke tests on WSL2 merge
  `collector/test/smoke/testdata/memory-limiter-mib.yaml` over them, because the collector
  cannot read a cgroup limit there.
- **Graceful scale-down.** The gateway has `preStop` sleep 15 s, so the agents' resolvers drop
  the pod first. Then `tail_sampling` decides the pending traces (`decision_wait` 30 s) and the
  exporter flushes (10 s). `terminationGracePeriodSeconds` 75 s covers all three.
- **Credentials.** `make kind-up` generates them as Secrets and none is committed:
  - the CA and the agent and gateway certificates (valid 30 days);
  - the tenants' htpasswd (`tenant-a`, `tenant-b`, `tenant-eval`) and their plaintext
    passwords, used by the bench and the agentic-rag capture. `make kind-up` regenerates both
    when a tenant is missing from them;
  - the ClickHouse password;
  - the Postgres password (`traceblame/postgres-credentials`).

## Runbook-agent sandbox (#13)

`make kind-runbook-up` (after `make kind-deploy`) adds two namespaces for the runbook-agent
capture; `make kind-runbook-down` deletes them. The capture applies the agent and the tee
collector itself, with the image it built.

| Path | What |
|---|---|
| `runbook/manifests/10-rbac.yaml` | The agent's ServiceAccount and a Role in `runbook-sandbox` only: the verbs of its actions (pods, events, logs, deployments, `deployments/scale`). No ClusterRole; no delete, exec or Secrets. |
| `runbook/manifests/20-monitoring.yaml` | `runbook-monitoring`: kube-state-metrics (sandbox only), Prometheus, Alertmanager and blackbox_exporter, pinned by digest in tools/versions.env. |
| `runbook/manifests/30-network.yaml` | The agent takes webhooks only from Alertmanager and reaches only DNS, the API server, the tee and the host's Ollama (or the canary's stub LLM). The tee forwards only to `observability/otel-agent`. |
| `runbook/monitoring/rules.yml` | Four alert rules, expressions and annotations verbatim from samber/awesome-prometheus-alerts at the pinned commit (vendored under tools/fixtures/runbook_agent/upstream/); only names, labels and `for:` are overridden. |
| `runbook/sandbox/` | Templates of the agent Deployment and the tee collector, applied by the capture. |

- **Derived addresses.** `kind-runbook-up` reads the API server's address and port from the
  `kubernetes` EndpointSlice (exactly one address) and resolves `host.docker.internal`
  inside the cluster. Nothing is fixed in the manifests. Before any task, the capture fails
  unless the applied policy still matches the live endpoint and that address, the agent
  reaches the API server and Ollama, and it cannot reach ClickHouse.
- **One webhook per task.** Alertmanager groups by alert, namespace and service, waits 15 s,
  never repeats within a run and does not send resolved alerts; an inhibit rule keeps the OOM
  pod's crash-loop alert quiet. The capture counts Alertmanager's webhook requests
  (`alertmanager_notification_requests_total`, not `notifications_total`, which also counts
  resolved-only flushes that send nothing).
- **Slow rules.** The OOM rule compares restarts with 10 minutes ago, so OOM workloads start at
  the beginning of a run and are triggered later. The crash-loop rule looks back 5 minutes, so
  each crash task waits about that long for its alert to clear.

## Known limitations

- **Split traces while the gateway set changes** (design §1.1 deployment notes). After a ring
  change, a trace's later spans can go to another gateway, and each half is sampled
  independently. The bench measures how often this happens and for how long:
  `evals/reports/gateway-scaling-*.md`. Mitigation: #38.
- **The low-eval-score policy (§1.1) is not configured.** No profile attribute carries an
  eval score at ingest (#37).
- **App → agent is plain gRPC/HTTP inside the node** (ADR-0005, negative consequences).
